## Контекст: что вообще такое Jungian Profiler

**Суть.** Движок TrueNeverStory (далее TNS) адаптирует сюжет под игрока. Для этого
есть подсистема «юнгианский профайлер» — она незаметно анализирует поведение игрока
и определяет его **психотип** (по юнгианской типологии — те самые 16 типов: INTJ,
ENFP и т.д.), а затем **подстраивает стиль повествования** под этого игрока.

**Как это устроено (коротко):**

- Профиль игрока хранится в БД (таблица `player_style_profiles`, колонки с префиксом
  `jungian_`). Это набор «осей» (например, мышление ↔ чувство, сенсорика ↔ интуиция
  и т.п.), у каждой оси есть значение, разброс (`range`) и уверенность (`confidence`).
- Профиль собирается из двух источников: текст игрока (`source: 'text'`) и
  поведенческие метрики (`source: 'metrics'`), которые сливаются функцией
  `blendBehavioralSignals` (`source: 'blended'`).
- Когда уверенность профиля достигает `confidence >= 0.3`, включается адаптация:
  функция `Director.computeDistribution` (чистая, без LLM) даёт веса, и конвейер
  агентов (Dramaturg → Actor → Validator → Stylist → Censor) пишет текст «под игрока».
- Всё сидит за флагом `jungian-profiler-enabled` (по умолчанию `false`). Откат — просто
  переключить флаг, ничего ломать не надо.
- Отдельно есть **AuthorMatcher**: при создании персонажа подбирается «ближайший по
  стилю» классический автор (по embedding-поиску), его фразы подмешиваются в промпт
  Stylist как few-shot примеры.

**Что уже сделано.** Все 4 фазы (`docs/compose/plans/2026-08-14-jungian-profiler-*.md`)
реализованы, закоммичены, запушены в `origin/main` и проверены: 1266 тестов pass /
0 fail, `tsc --noEmit` чист. Чекбоксы в файлах плана проставлены `[x]`.

**Что в этом файле.** Только то, что **осознанно отложено или сделано частично** —
это не пропущенная работа, а решения, зафиксированные в спеке v1.3
(`docs/compose/specs/2026-08-10-jungian-profiler-design_1.3.md`). Каждый пункт ниже
объяснён: что это, зачем, и что конкретно делать, если вернёшься.

## 1. Сделано ЧАСТИЧНО — на это можно вернуться

### 1.1. Экономическая адаптация под психотип (пункт S13 в спеке)

- **Что это.** Идея была: подстраивать под психотип игрока не только ТЕКСТ, но и
  ЭКОНОМИКУ — цены, награды, сложность сделок, налоговые дилеммы. Например,
  рискованному игроку — более волатильные цены и рискованные квесты, осторожному —
  стабильные.
- **Что сделано.** Только один маленький кусочек: в `buildPlayerVoice` есть
  `sample(dist.informationStyle)` — то есть «сколько информации выдавать игроку»
  семплируется из его профиля. Это про ПОРЦИЮ ТЕКСТА, а не про экономику.
- **Что НЕ сделано.** Полноценной привязки экономических подсистем
  (`EconomicService`, `npc-economy.ts`, `slave-economy.ts`, `economic-cycles.ts`,
  `faction-tax-dilemma.ts`) к профилю игрока не было вообще — в плане такой отдельной
  задачи не существовало.
- **Что делать, если вернёшься.** Сначала спроектировать (какие именно экономические
  параметры зависят от каких осей психотипа), потом отдельной фазой/спекой. Не трогать
  экономику «на ходу» — она живёт в 4 модулях и имеет фасад `EconomicService`.

## 2. Отложено на v1.4 (enhancement, «по результатам A/B»)

Эти вещи имеют смысл делать ТОЛЬКО после того, как нынешняя версия поживёт и можно
будет сравнить A/B (с флагом включён/выключен). Не делать «заранее» — сначала данные.

### 2.1. Затухание уверенности при простое >7 дней (часть S15)

- **Что это.** Профиль игрока хранится между сессиями (это уже работает — roundtrip в
  БД). Но если игрок не заходил больше недели, его старый профиль мог устареть
  (человек мог сменить стиль игры). Нужно «затухание»: чем дольше игрока не было, тем
  ниже `confidence`, чтобы движок не навязывал устаревший психотип.
- **Зачем.** Без этого движок уверенно продолжает подстраиваться под игрока, которого
  уже «нет», и адаптация становится неточной.
- **Сейчас.** Нет никакого decay — `confidence` не уменьшается от бездействия.
- **Что делать.** Добавить при загрузке профиля проверку времени последнего апдейта:
  если прошло >7 дней — умножить `confidence` (или оси) на понижающий коэффициент.
  Пункт про сам roundtrip (сохранение/чтение) уже реализован в Task 1.4 — трогать не надо.

### 2.2. Per-axis confidence gates (гейт по каждой оси отдельно)

- **Что это.** Сейчас адаптация включается по ОДНОМУ общему порогу:
  `profile.confidence >= 0.3`. Если ниже — `Director` возвращает равномерное
  распределение (все веса одинаковы = адаптации нет вообще).
- **Зачем улучшать.** У разных осей уверенность разная: по «мышление/чувство» движок
  может быть уверен на 0.6, а по «интуиция/сенсорика» — только на 0.1. Сейчас из-за
  одного общего гейта слабоуверенная ось либо тянет всё вниз, либо игнорируется целиком.
  Правильнее — включать адаптацию отдельно по каждой оси, где своей уверенности хватает.
- **Сейчас.** Только общий гейт. Per-axis — нет.
- **Что делать.** В `Director.computeDistribution` (и/или в месте применения гейта)
  заменить один `if (confidence >= 0.3)` на поосевую логику. Нужны отдельные пороги на
  ось. Делать ПОСЛЕ A/B, чтобы понять, какие пороги реально дают эффект.

### 2.3. Warmup-логика для `range` (разброса)

- **Что это.** У каждой оси есть не только значение, но и `range` — насколько движок
  «не уверен» в точном значении (разброс). Сейчас `range` набирается естественным
  путём: нужны ~200 ходов наблюдений, прежде чем он станет осмысленным (холодный старт).
- **Зачем улучшать.** 200 ходов — это долго: первую пару часов игры адаптация по
  `range` почти слепая. Можно «разогреть» range быстрее — посчитать его из дисперсии
  первых N сигналов (bootstrap), а не ждать, пока накопится статистика.
- **Сейчас.** Только медленный естественный набор. Warmup-логики нет.
- **Что делать.** В логике обновления осей (blend/`updateAxis`) добавить начальную
  оценку `range` из дисперсии первых сигналов. Отложено на v1.4.

### 2.4. Отдельная система обнаружения аномалий

- **Что это.** Детектор резких аномальных изменений поведения (игрок внезапно сменил
  стиль, либо данные «шумят»). Нужна, чтобы движок не гонялся за случайными выбросами.
- **Сейчас.** Нет отдельной системы.
- **Что делать.** Только «при необходимости» (v1.4) — если по факту окажется, что
  профиль дёргается. Не делать превентивно.

## 3. Out of scope v1.3 (раздел S19) — НЕ запланировано в этом цикле

Это вещи, которые **сознательно не вошли в v1.3** и НЕ реализовывались. В этот список
стоит заглянуть, если захочешь расширять профайлер дальше.

### 3.1. Ручной сброс психотипа через UI

Позволить игроку (или админу) вручную обнулить/пересоздать профиль психотипа из
интерфейса. Сейчас профиль только накапливается автоматически.

### 3.2. Визуализация распределения в UI

Показывать игроку/разработчику график его психотипа (какие оси доминируют) прямо в
веб-интерфейсе. Сейчас визуального представления нет — профиль живёт только в БД/логах.

### 3.3. Big Five (OCEAN) — версия 2+

Альтернативная модель личности: Openness / Conscientiousness / Extraversion /
Agreeableness / Neuroticism. Сейчас используется юнгианская типология (16 типов).
Big Five — это другой, более «психологический» фреймворк. Планировалось как v2+,
отдельным большим этапом. Не смешивать с текущими осями.

### 3.4. Нейросетевой маппинг «поведение → психотип»

Сейчас связь «действие игрока → сдвиг оси» задана вручную (правила в коде). Идея на
будущее — обучить/использовать модель, которая сама сопоставляет поведение с
психотипом. Это большой исследовательский кусок, в v1.3 не входил.

### 3.5. NPC-to-NPC автономные взаимодействия (без игрока)

NPC сами общаются/конфликтуют между собой, пока игрок не участвует. Сейчас все
взаимодействия так или иначе завязаны на действия игрока.

### 3.6. Хранение истории отдельных действий

Сейчас хранятся только **агрегаты** (счётчики: сколько раз рискнул, сколько раз
избегал диалога и т.п.). Сырая история каждого действия НЕ пишется — её нельзя
воспроизвести. Хранение полной истории отдельных действий отложено (дорого по месту
и не нужно текущей логике).

### 3.7. Manipulation detection как отдельная система

Определение, когда игрок «манипулирует» системой (например, намеренно генерит однотипные
действия, чтобы накрутить нужный психотип). Отдельной системы нет.

  `authorPhrases`).
